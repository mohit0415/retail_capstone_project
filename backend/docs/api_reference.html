Known traps

Authentication

Every endpoint except GET /health needs an Auth0 access token (RS256, validated against the tenant JWKS; roles come from the https://stateful-agent.com/roles claim) and Authorization: Bearer <token>. The token is a JWT signed with JWT_SECRET, valid for JWT_EXPIRY_MINUTES (60 by default).

The role you mint the token with is not a label — it is compiled into scopes at mint time, and those scopes decide which policy documents retrieval may search and which database tables the SQL path may read. You cannot widen them per request; document_scope on /ask only ever narrows.

Token claims

{
  "sub": "mohit",
  "role": "compliance_officer",
  "departments": ["Finance"],
  "scopes": ["doc:anti_bribery_policy", "doc:gdpr", ...,
              "table:vendors", "table:audit_logs", ...,
              "risk:High", "risk:Critical", ...],
  "iat": 1767225600,
  "exp": 1767229200
}
In Swagger, paste the token on its own. Click Authorize and paste only the access_token value — Swagger adds the word Bearer itself. A leading Bearer , a stray quote, or a newline picked up while copying all produce a 401, and the error body names which one it was.

The role also decides what a permitted call can actually reach. A store_associate may call /ask, but is granted no database table, so 0 of the 17 vetted SQL templates are in reach and a pure record question escalates rather than being answered from policy text. store_manager reaches 9; compliance_officer and above reach all 17.

GET /auth/me any role

What the Auth0 token resolved to on the backend. Tokens are minted by Auth0 (Universal Login in the React frontend), never here: src/auth/security.py checks signature, audience, issuer and expiry against the tenant JWKS, then maps the roles claim onto the five backend roles (the most privileged wins, user from practice-1 maps to store_associate, no recognised role is a 403).

Responses

200 MeResponse — user_id (the sub claim), role, departments, access_scopes (doc:*, table:*, risk:*), auth0_roles, permissions flags, screens the frontend may open and azure_configured.
401 Missing, expired, wrong-audience or badly signed token.
403 Valid token, but none of the Auth0 roles is one of the five backend roles.
POST /auth/azure any role

Applies the Azure OpenAI credentials the user typed on the frontend login page. They are never stored in a frontend .env; the frontend sends them once after the Auth0 login.

Request body

endpointrequired · string
https://<resource>.openai.azure.com/
api_keyrequired · string
The Azure OpenAI key.
api_version, small_deployment, strong_deployment, embedding_deploymentoptional
Default 2024-10-21, gpt-4o-mini, gpt-4o, text-embedding-3-small.
verifyoptional · bool
Default true: one tiny embedding call and one tiny chat call are made before the values are applied.

Example

curl -s -X POST http://localhost:8000/auth/azure \
  -H 'Authorization: Bearer $TOKEN' -H 'Content-Type: application/json' \
  -d '{"endpoint":"https://demo.openai.azure.com/","api_key":"...","small_deployment":"gpt-4o-mini"}'

Responses

200 AzureCredentialsResponse — azure_configured, verified, the endpoint host and deployment names now in use.
400 Verification failed — the detail names the deployment that rejected the key.
422 Endpoint not https:// or a required field missing.
POST /ask any role

The one question endpoint. Runs the full graph: guardrail → rewrite → intent → entity resolution → risk fusion → planner → one of five evidence paths → validation → confidence → release or escalate.

Headers

Authorizationrequired
Bearer <access_token>
Idempotency-Keyoptional
Any string. The cache key is this value combined with your user_id and the request body, so replaying the same key with the same body returns the stored response and its original status code without re-running the graph.

Request body

queryrequired · string
3 to 2000 characters. Shorter or longer is a 422 before the graph starts.
thread_idoptional · string
Omit it on the first turn and the response hands you one. Pass it back on a follow-up and the prior turns plus the rolling thread summary are used to rewrite your question into a standalone one — so "what about that vendor" resolves before retrieval, routing and risk ever see it.
document_scopeoptional · string[]
Narrows retrieval to named document types. It can only ever narrow: a value outside your role's grant is a 422 that names what you did ask for and lists what the role accepts.

Example

curl -s -X POST http://localhost:8000/ask \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-001' \
  -d '{"query":"Which vendors are overdue for review?"}'

# follow-up in the same thread
curl -s -X POST http://localhost:8000/ask \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"query":"and what does the policy require for those?",
       "thread_id":"<thread_id from the first response>",
       "document_scope":["vendor_policy"]}'

Four outcomes, two status codes

One endpoint returns four different bodies. Read the status field — it is the discriminator, and the HTTP code alone does not tell the three 200 shapes apart.

200
answered

Certified. Carries the answer, citations, optional SQL proof, confidence, risk level and stage timings.

200
refused

The input guardrail or the intent classifier rejected it — out of scope, or a prompt-injection attempt. Carries a reason, no answer.

200
clarification_required

A named entity matched nothing, or matched several rows. Carries a question and the candidate rows. Reply in the same thread.

202
pending_review

Queued for a human. No draft answer is returned — the reason it escalated is that this answer could not be certified. Poll poll_url.

200 · answered

{
  "status": "answered",
  "request_id": "3f2a…", "thread_id": "9c81…",
  "answer": "Three vendors are past their next review date as of 2025-12-31 …",
  "citations": [{ "document_title": "Supplier & Vendor Compliance Policy",
                  "clause_number": "4.2", "section": "Review Cadence",
                  "version": "1.0", "excerpt": "Vendors shall be reviewed …" }],
  "sql_evidence": { "template_id": "vendors_review_overdue",
                    "statement": "SELECT … FROM vendors WHERE next_review_due < %(as_of)s …",
                    "parameters": {"as_of": "2025-12-31", "row_limit": "200"},
                    "row_count": 3, "as_of": "2025-12-31" },
  "confidence": 0.93,
  "risk_level": "Medium",
  "uncertainty_note": "",
  "evidence_path": "nl2sql",
  "degraded": false,
  "timings": {"t1_ms": 2140.5, "t2_ms": 3980.1, "t3_ms": 8210.7,
               "t4_ms": 11040.2, "total_ms": 11102.9}
}

evidence_path is one of rag, nl2sql, hybrid, agentic, high_risk_panel — which one is decided by the classified intent, not freely by the planner. degraded means an optional step was skipped under budget pressure, or only half the evidence was reachable; it costs 0.10 confidence.

202 · pending_review

{
  "status": "pending_review",
  "request_id": "3f2a…", "thread_id": "9c81…",
  "risk_level": "High",
  "reason": "risk fused to High, so the multi-agent panel is mandatory",
  "queued_at": "2026-09-05T10:14:22Z",
  "poll_url": "http://localhost:8000/requests/3f2a…",
  "timings": { … }
}

All responses

200answered · refused · clarification_required — discriminated by status.
202pending_review — a review row was written; poll the returned URL.
401No readable bearer token. The body names the likely copy-paste fault.
422query outside 3–2000 chars, or a document_scope value the role cannot read.
500The graph terminated with no draft and no terminal outcome. This is a bug, not a policy decision.
GET /requests/{request_id} any role

Polls an escalated request. This is the poll_url a 202 hands you.

Path parameter

request_idrequired · string
The request_id from the 202 body.
Only escalated requests exist here. This route reads the escalation_queue table alone, so a request that was answered normally at 200 has no row and returns 404. Poll it only for a request_id that came back as 202.

Example

curl -s http://localhost:8000/requests/3f2a… -H "Authorization: Bearer $TOKEN"

Responses

200Still queued — {"status":"pending_review","request_id":…,"risk_level":…}
200Reviewed — adds answer, reviewer_decision, thread_id, reviewed_at.
404Unknown request id — including any request that was answered rather than escalated.
GET /review/queue reviewer

Lists every request waiting on a human, oldest first. Takes no parameters.

Example

curl -s http://localhost:8000/review/queue -H "Authorization: Bearer $TOKEN"

Responses

200QueueItem[] — request_id, thread_id, user_id, risk_level, reason, queued_at. An empty list is a healthy queue, not an error.
403The token's role is not compliance_officer, legal_reviewer or admin.
GET /review/{request_id} reviewer

The full context package for one queued request — everything the reviewer needs to judge the answer without re-running anything.

Response · ReviewPackage

original_query
standalone_query
What the user typed, and what the rewriter turned it into. A rewrite that dropped a qualifier is usually the cause of a bad answer, and comparing these two is the fastest way to see it.
conversation_history
Prior turns in the thread.
retrieved_documents
The chunks the answer was built from, with their clause identifiers.
sql_evidence
Template id, the exact statement, bound parameters, row count and as-of date. null when no database probe ran.
validation_output
The structured defect list. Never a rewritten answer — the validator reports, it does not patch.
reasoning_trace
Per-node spans with timings, and the routing decision with the reason it was taken.
draft_answer
risk_level
confidence
What the system produced and how it scored itself.

Example

curl -s http://localhost:8000/review/3f2a… -H "Authorization: Bearer $TOKEN"

Responses

200ReviewPackage
403Not a reviewer role.
404Unknown request id.
POST /review/{request_id} reviewer

Records a decision and resumes the graph from its checkpoint. A human's answer passes the same output guardrail — PII scrub and citation check — as a machine's.

Request body

decisionrequired · enum
accept releases the draft as-is · edit releases edited_answer · reject records the decision and releases nothing.
edited_answeroptional · string
Required in practice for edit. If omitted, the original draft is used.
reviewer_notesoptional · string
Stored with the decision and kept as eval gold data.

Example

curl -s -X POST http://localhost:8000/review/3f2a… \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"decision":"edit",
       "edited_answer":"As of 2025-12-31, three vendors are past their review date …",
       "reviewer_notes":"tightened the count to name the as-of date"}'

Response · ReviewOutcome

Read resumed and released together — they answer two different questions.

  • resumed: true, released: true — the reviewed answer passed the output guardrail and went out. answer carries what was actually released, which may differ from what you submitted if the guardrail scrubbed it.
  • resumed: true, released: false — the graph ran but the guardrail rejected the reviewed answer, or the decision was reject. note says which.
  • resumed: false — the checkpoint for that thread was gone, so the decision is recorded but the answer never passed back through the guardrail. The endpoint reports this rather than pretending the answer was validated.

Responses

200ReviewOutcome — decision, resumed, released, outcome, answer, note.
403Not a reviewer role.
404Unknown request id.
409Already reviewed, or another reviewer won the race between the read and the write.
POST /ingest admin only

Uploads and indexes one policy document. Multipart, not JSON. The call blocks until the document is parsed, chunked, embedded and written — it is not a background job.

Form field and query

filerequired · multipart
.md · .pdf · .docx · .txt. Maximum 20 MB (UPLOAD_MAX_BYTES). The upload is spooled to a temp file and deleted afterwards either way.
forcequery · bool · false
Re-ingest a document whose version already exists, superseding the old nodes.

Example

curl -s -X POST "http://localhost:8000/ingest?force=false" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -F "file=@Documents/Supplier_Vendor_Compliance_Policy.pdf"

Responses

200indexed — node counts by kind: text_nodes, table_nodes, image_nodes, superseded_nodes, plus doc_type, version and parsed_with.
200skipped — already indexed at this version, or parsing produced nothing indexable. reason says which.
400No filename, or the file is empty.
403Not admin.
409Embedding model mismatch. The vector table holds vectors from a different embedding model. Ingesting anyway would make retrieval return confident nonsense, so it is refused.
413Over the size limit; the body states the actual size and the cap.
415Unsupported extension.
422The pipeline rejected the document's content or metadata.
500Ingestion failed; the body names the file and the underlying error.
GET /ingest/status admin only

What is actually in the index right now. Takes no parameters. This is the first thing to check when /ask answers "the extracts do not settle this" for a question you know is covered.

Response · CorpusStatusResponse

indexed
Whether every file in the corpus directory has nodes in the vector table.
corpus_dir
Resolved from POLICY_CORPUS_DIR.
embed_model
embed_model_compatible
The active embedding model, and whether it matches the vectors already stored. When this is false, retrieval is unreliable and ingestion is blocked until the table is rebuilt.
documents
Per-document node counts, grouped by doc type, version and parser.
unindexed_files
Files present on disk with no nodes in the index. A non-empty list here explains a half-empty knowledge base.

Example

curl -s http://localhost:8000/ingest/status -H "Authorization: Bearer $ADMIN_TOKEN"

Responses

200CorpusStatusResponse
403Not admin.
POST /ingest/rebuild admin only

Empties the vector table and re-ingests every document in the corpus directory. This is the repair for an embedding-model mismatch.

Guarded by a required confirmation. Without ?confirm=true it returns 400 and explains the cost rather than doing anything. It is one full embedding pass over the whole corpus, and it is destructive before it is constructive — the table is cleared first.

Query parameter

confirmrequired · bool
Must be true. Defaults to false, which is a 400.

Example

curl -s -X POST "http://localhost:8000/ingest/rebuild?confirm=true" \
  -H "Authorization: Bearer $ADMIN_TOKEN"

Responses

200RebuildResponse — cleared_chunks, indexed_files, skipped_files with reasons, total_nodes, and the same documents / unindexed_files summary as the status route.
400confirm was not true. Nothing was touched.
403Not admin.
409The corpus directory does not exist. Checked before clearing, so the index survives.
500Either the clear failed, or the clear succeeded and re-ingestion failed. The second message says so explicitly, because that state leaves the index empty.
GET /metrics/slo reviewer

Latency percentiles per t0–t4 stage against configured targets, over a rolling window.

Query parameter

hoursoptional · int · 1–720
Window size. Defaults to SLO_WINDOW_HOURS (24).

The five measurement points

MarkMeaningTarget p95
t0Request accepted, after auth and the input guardrail—
t1Intake complete: rewrite, intent, entities, risk6 000 ms
t2Evidence plan ready and the route decided9 000 ms
t3Evidence gathered and the answer drafted20 000 ms
t4Validated, scored, released or escalated27 000 ms

Marks are cumulative from t0, so they read as a timeline rather than a set of durations, and they are carried forward on an early escalation so percentiles are not computed over a shifting population.

Example

curl -s "http://localhost:8000/metrics/slo?hours=24" \
  -H "Authorization: Bearer $TOKEN"

Responses

200SloReport — per-stage p50/p95/p99 with pass or fail, a total, breached_stages, breached_paths, outcome counts, and per-evidence-path latency scored against that path's own target.
403Not a reviewer role.
422hours outside 1–720.
503The latency history could not be read — usually the database is down.
GET /health no auth

Liveness plus the configuration the answers actually depend on. Unauthenticated, so it is safe for a load balancer — and worth reading yourself before blaming the model for a bad answer.

Example and response

curl -s http://localhost:8000/health

{
  "status": "ok",                        // "degraded" when the database is down
  "database": "up",
  "audit_log": {"state": "closed", …},    // audit circuit breaker
  "escalation_queue_depth": 2,
  "as_of_date": "2025-12-31",             // every figure is pinned to this
  "confidence_threshold": 0.75,
  "deadlines_seconds": {"standard": 30.0, "hybrid": 45.0,
                         "agentic": 75.0, "high_risk": 90.0},
  "default_token_budget": 48000,
  "azure_configured": true              // false means no LLM calls will work
}
Two fields here explain most surprising answers. as_of_date is the date every figure is pinned to — nothing in the system reads the wall clock, so a "current" question is answered as of 2025-12-31. And a deadlines_seconds value below the floor means the settings validator raised it at startup; treat that as a bug in your .env, not a safety net doing its job.

Responses

200Always 200 while the process is up. Read status and database for the actual verdict.

Known traps

Rate limiting is configured but not active

main.py builds a Limiter, assigns it to app.state.limiter and registers the 429 handler — but never adds SlowAPIMiddleware, and no route carries a @limiter.limit(...) decorator. In slowapi, that middleware is what applies default_limits to requests. So RATE_LIMIT_STANDARD=30/minute and RATE_LIMIT_HIGH_RISK=10/minute currently do nothing. One line fixes it:

from slowapi.middleware import SlowAPIMiddleware
app.add_middleware(SlowAPIMiddleware)

CORS is wide open

allow_origins=["*"] together with allow_credentials=True. Fine on localhost, wrong anywhere else.

/auth/azure is process-wide

Any authenticated role can call it and the credentials apply to every request the process serves from then on. That matches the login-page flow (every user types them), but it means one user's key is used for everyone until the next call.

The poll_url only works for escalations

Covered above under GET /requests/{id}, and worth repeating because it looks like a general-purpose status route and is not one.

Idempotency keys cache the failure too

The store keeps the status code alongside the body, so replaying a key that produced a 202 returns that 202 again without re-running the graph. Use a fresh key when you want a genuine retry.
